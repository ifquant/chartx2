# 0063: 把 `Workbench` 示例数据抬到 `1 万根 K 线`

这次提交没有继续补新的图表类型，而是把默认 `Workbench` 的示例数据量从几十根提升到了 `10,000` 根 K 线。

## 为什么现在做这个

`chartx2` 的 `Workbench` 不只是一个首页，它是“完整图表工作台示例”。如果默认示例只挂几十根数据，那么很多底层能力其实没有在更接近真实使用的压力下被展示出来：

- 时间轴压缩行为
- 首屏可见范围选择
- pan / zoom 的体感
- volume pane 在大数据量下的表现

所以这一步的目的是让默认工作台更像真实图表软件的使用场景，而不是继续像一个教学 demo。

## 这次改了什么

更新文件：

- [chartx-demo.ts](/Users/dev/workspace2/hc_apps/chartx2/src/lib/demo/chartx-demo.ts)

核心改动很小但影响面很实：

- `mountWorkbenchDemo(...)` 里的主图数据量从 `52` 根抬到 `10_000` 根
- volume 和 study line 仍然复用这同一批 bars 派生出来的数据

也就是说，当前完整工作台示例现在默认就是一个大数据量图，而不是一张小样图。

## 会带来什么变化

### 1. 首页体感更接近真实 chart terminal

默认打开就会看到压缩后的长历史数据，而不是几根大蜡烛填满画布。这更符合用户对股票/期货图表软件的直觉。

### 2. `timeScale` 和 viewport 更有意义

在几十根数据时，缩放/平移的意义有限；在 `10,000` 根数据时，这些交互会更接近真实使用。

### 3. 视觉回归也变得更严格

因为默认 `Workbench` 的截图基线会一起更新，所以任何后续对大数据量默认视图的破坏，都更容易被发现。

## 验证

这次实际跑过并通过：

```bash
pnpm check
pnpm test:visual --update-snapshots
pnpm build
```

## 这次没有做的事

这一步只放大了 `Workbench` 的默认数据量，没有同步把所有 feature tabs 都抬到 `10,000` 根。这样做是为了保持切片可控，不把所有特性页都一起拖进新的性能和视觉基线变化里。

另外，这次也没有顺手修改本地性能 smoke 预算。`phase-one-performance` 仍然保留它原本的 `2K / 5K` 本地 smoke 定位。

## 给新人的 2 个知识点

### 1. 为什么示例程序的数据量也属于“底层能力展示”

因为很多图表问题只有在数据量上来以后才暴露出来。比如：

- 可见范围太挤
- 初始 bar spacing 不合适
- 轴标签开始难看
- pan/zoom 体感变差

所以 demo 的数据量不是纯展示问题，它也会影响你能不能真实看见底层能力。

### 2. 为什么这次只放大 `Workbench`

因为 `Workbench` 是完整示例，最适合先承受真实数据量压力。feature tabs 更偏“聚焦展示某一项能力”，它们不一定都需要同时切到大数据量，否则每次底层小变动都会让一大串基线一起剧烈变化。
